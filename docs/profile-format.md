# 価値尺度ファイルの形式

価値尺度ファイルは、1 人の 1 つの質問について、質問の定義と 2 択の回答をまとめた JSON ファイルです。あなたの価値尺度は、この軽量な 1 つのファイルに保存して、他の人と共有できます。ファイルに入っているのは補正の結果（768 次元の価値尺度ベクトル）ではなく回答そのものなので、読み込む側はいつでも回答から価値尺度ベクトルを作り直せます。同じ埋め込みモデルを使っていれば、別のアプリや別のデータセットでも使え、人と交換することもできます。

## なぜ価値尺度ベクトルではなく回答を保存するのか

価値尺度ベクトル（768 個の数字）だけを保存すれば、ファイルは約 1 KB で済みます。それでも回答を保存しているのは、次の 4 つのためです。

1. **続きから答えられる。** ベクトル 1 本には「どれくらい確かか」（事後分布の広がり）が入っていません。Shiken は、次に聞く組を選ぶときにも、答える前の予想の確率にもこの広がりを使うので、ベクトルだけを受け取ると、そこから先を正しく補正し続けられません。回答があれば、広がりも含めて作り直せます。
2. **個別の加減点を失わない。** 「傾向とは関係なく、この項目だけは好き」という項目ごとの上げ下げは、向き 1 本では表せません。回答があれば、同じデータセットで使うときに加減点も作り直せます。
3. **読み込む側のデータセットに合わせられる。** 補正は比較用の集合で標準化してから行うので、同じ回答でもデータセットが違えば、作られる価値尺度ベクトルが少し変わります。回答を持っていれば、読み込む側のデータセットに合わせて作り直せます。
4. **計算のしかたを良くしても、古いファイルが使える。** 補正の方法を改良したときも、回答から新しい方法で作り直せます。

埋め込みモデルをまたぐ場合も、回答があれば作り直せることがあります。保存した埋め込みベクトルはモデルが違うと使えませんが、どの項目とどの項目を比べてどちらを選んだかは残っているので、元の画像や文が手元にあれば、新しいモデルで埋め込み直して補正できます。

その代わり、ファイルは数十〜数百 KB になり、答えた項目がある程度推測できるようになります（下の「個人のデータとしての扱い」）。ベクトル検索で並べ替えるときのように価値尺度ベクトルだけが要る場面では、[`weight_vector()`](python.md#1-本のベクトルにする) で書き出せます。

## 例

```jsonc
{
  "format": "shiken-profile",
  "version": 1,
  "question": {                          // 質問の定義
    "type": "score",
    "levels": [[1, "全然美味しくなさそうな料理の写真"], [5, "最高に美味しそうな料理の写真"]]
  },
  "question_embeddings": {              // 質問の説明の埋め込みベクトル（説明の順。形式は items と同じ）
    "descriptions": [{"emb": "…", "scale": 0.0012}, {"emb": "…", "scale": 0.0011}]
  },
  "concepts": {                          // 補正に使った概念の語（同じ語で補正し直すため）
    "name": "food",
    "noun": "料理の写真",
    "words": ["揚げ物", "焼き料理", "辛い", "..."]
  },
  "encoder": {                           // 埋め込みベクトルの作り方。name が一致するときだけ保存した埋め込みベクトルを使う
    "name": "google/embeddinggemma-2",
    "model": "google/embeddinggemma-2",
    "revision": "914f7f89142e33e77833254d9c9b90c3cef7303b",
    "options": {"doc_prompt": true, "audio_max_seconds": 320}
  },
  "answers": [                           // 回答の履歴。順番に意味がある
    {"a": "dish-0012", "b": "dish-0087",
     "y": 1,                             // 1: a が選ばれた / 0: b / 0.5: 同じくらい
     "predicted": 0.62}                  // 答える前の予想（a が選ばれる確率）
  ],
  "items": {                             // 回答に出てくる項目。キーは answers の a / b
    "dish-0012": {
      "emb": "…",                        // 埋め込みベクトルを int8 にしたもの（base64）
      "scale": 0.00123                   // int8 から実数に戻す倍率
    }
  }
}
```

## 各部分の決まり

- **項目の名前（answers の a / b、items のキー）** は、組み込む側が決める文字列です。ファイルのパスでも商品の ID でもかまいません。同じ項目には同じ名前を使います。個別の加減点はこの名前に結びつきます。
- **埋め込みベクトル** は、元の次元のまま int8 にして持ちます。使うときは `emb × scale` を長さ 1 に正規化し直します。int8 にしても、素の価値尺度でのスコアリングとパーソナライズの正解率は float のときと変わりませんでした（[試した範囲での結果](evaluation.md#埋め込みベクトルを小さくしたとき)）。1 項目は 768 次元で 772 バイト（base64 で約 1 KB）、100 問・約 200 項目のファイルで 200 KB ほどです。
- **question_embeddings** は、質問の説明を埋め込んだベクトルです。説明が画像や音の場合、読み込む側に元のファイルがあるとは限らないので、ファイルに入れます。埋め込みモデルが同じなら、説明が文の場合もこのベクトルを使います。はい／いいえの質問で中立の文を使った場合は、その埋め込みベクトルも `neutral` として入ります。
- **encoder** の `name` が読み込む側のエンコーダの `name` と違う場合、保存した埋め込みベクトルは使いません。空間が別物で、混ぜると意味のない値になるためです。そのときは、読み込む側のデータセットにある項目への回答だけを補正に使います。
- **predicted** は答える前の予想です。これを並べると、回答が進むにつれて予想が当たるようになったか（価値尺度が本人に合ってきたか）が分かります。
- **個別の加減点の大きさ** はファイルに持たず、読み込むたびに回答から決め直します。

## 個人のデータとしての扱い

価値尺度ファイルからは、本人の好みが分かります。また、答えた項目の埋め込みベクトルが入っているので、元のファイルが無くても「何に答えたか」をある程度推測できます（埋め込みベクトルが近い画像を探せば、似た画像が見つかります）。

Shiken は価値尺度ファイルをどこにも送りません。保存先と共有のしかたは組み込む側が決めます。共有する機能を作る場合は、利用者にこのことを伝えてください。

## 未決の点

- **比較用の集合を持ち運ぶか。** スコアの標準化と特徴の中心化は、比較用の集合（既定ではデータセットそのもの）で行います。データセットが違えば、同じ回答からでも補正の結果が少し変わります。比較用の集合の要約（平均など）をファイルに入れるかは決めていません。
- **回答の時刻を持つか。** 今は順番だけです。時刻があると好みの移り変わりを見られますが、個人のデータとしての重みが増します。
