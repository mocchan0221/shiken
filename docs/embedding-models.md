# 埋め込みモデル

Shiken の本体は、どの埋め込みモデルの埋め込みベクトルでも使えます。条件は、データセットの項目（画像や音）と質問の説明を同じ空間に埋め込めることです。

## 既定のモデル: EmbeddingGemma 2

付属のエンコーダ（`pip install "shiken[eg2]"`）は、Google の EmbeddingGemma 2（`google/embeddinggemma-2`、7.4 億パラメータ）を使います。画像・音声・動画・文を同じ 768 次元の空間に埋め込めます。この文書の数字はすべてこのモデルで測ったものです。

| 項目 | 内容 |
| :-- | :-- |
| 大きさ | 約 1.4 GB（初回に Hugging Face から取得） |
| 計算 | GPU があれば GPU、無ければ CPU。結果はディスクに保存して再利用する |
| 質問の説明（文） | `SearchQuery` のプロンプトで埋め込む |
| データセットの項目 | 文書のプロンプト（`title: none \| text: `）付きで埋め込む |
| 音声 | 曲をまるごと渡す。320 秒を超える曲は最後の 320 秒を使う |
| 数値の型 | GPU では bfloat16、CPU では float32（float16 では計算が壊れるので使わない） |
| ライセンス | Gemma の利用規約 |

EmbeddingGemma 2 を商用のプロダクトに組み込む場合は、Gemma の利用規約を確かめてください。Shiken のコードのライセンスとは別に適用されます。

## ほかのモデルを使う

分野によっては、その分野に強いモデル（服なら FashionSigLIP、音楽なら CLAP など）の方が合う可能性があります。エンコーダの形（`name`、`embed_texts`、必要なら `embed_files`）を満たすクラスを書けば差し替えられます（[Python で使う](python.md#埋め込みベクトルを用意する)）。

```python
class MyCLIP:
    name = "openai/clip-vit-large-patch14@<版>"
    def embed_texts(self, texts):
        ...  # 長さ 1 に正規化した (len(texts), 次元) の配列を返す
```

`name` は価値尺度ファイルに記録され、読み込むときに保存した埋め込みベクトルを使えるかの判断に使います。モデルの版や前処理を変えたときは名前も変えてください。

## ほかのモデルで確かめた結果

EmbeddingGemma 2 を主に使って作りましたが、ほかの 5 つの埋め込みモデルでも動くことを確かめました（2026-10-28、RTX 3070 Ti 8 GB）。どれもエンコーダのクラスを書くだけで、Shiken の本体は変えずに動きました。推奨ではなく、拡張したい人のための記録です。

| モデル | ライセンス | 入力 | 次元 | 回答 0 問のラベル照合 | 答えたあと（画像と文） | 答えたあと（音楽） | 画像 1 枚 | VRAM |
| :-- | :-- | :-- | --: | --: | :-- | :-- | --: | --: |
| EmbeddingGemma 2（既定） | Gemma の利用規約 | 文・画像・音声・動画 | 768 | +0.55 | 0.54 → 0.64 | 0.54 → 0.78 | 0.08 秒 | 2〜6 GB |
| SigLIP 2（`google/siglip2-so400m-patch16-384`） | Apache-2.0 | 文・画像 | 1152 | +0.32 | 0.51 → 0.65 | — | 0.04 秒 | 2.5 GB |
| Qwen3-VL-Embedding-2B | Apache-2.0 | 文・画像・動画 | 2048 | +0.52 | 0.54 → 0.61 | — | 0.29 秒 | 7.1 GB |
| Ovis-VL-Embedding-2B | Apache-2.0 | 文・画像・動画 | 2048 | +0.58 | 0.56 → 0.64 | — | 0.29 秒 | 5.4 GB |
| Ovis-Omni-Embedding-3B（8 ビットに量子化） | Apache-2.0 | 文・画像・音声・動画 | 2048 | +0.55 | 0.54 → 0.64 | 0.53 → 0.72 | 1.7 秒 | 7.4 GB |
| Omni-Embed-Nemotron-3B（8 ビットに量子化） | 非商用（研究・開発のみ） | 文・画像・音声・動画 | 2048 | +0.52 | 0.57 → 0.64 | 0.53 → 0.76 | 1.5 秒 | 8.2 GB |

- **回答 0 問のラベル照合** は、デモの画像 6 セットと小説のあらすじの 21 問で、素の価値尺度の並びと生成時のラベルとの順位相関の平均です（[素の価値尺度と正解ラベルの照合](evaluation.md#素の価値尺度と正解ラベルの照合) と同じ考え方）。質問は日本語のままです
- **答えたあと** は、著者の価値尺度ファイル（画像と文 8 個、音楽 4 個、30〜147 問）の回答を各モデルで埋め込み直し、10 分割の交差検証で 2 択の正解率を「素の価値尺度だけ → 補正後」で出したものの平均です。出題の組は EmbeddingGemma 2 が選んだものです
- **画像 1 枚** と **VRAM** は、その GPU での目安です。3B の 2 つは 8 GB に収まらず、ピークで共有メモリにあふれていたので遅く出ています

分かったこと:

- 補正の仕組みはモデルを選びません。どのモデルでも、答えると正解率が平均で 0.07〜0.15 上がりました
- SigLIP 2 は日本語の質問が苦手で、回答 0 問の並びが弱く、あらすじのような長い文はほとんど並べられませんでした（文は 64 トークンで切れます）。画像だけの価値尺度ファイルでは、補正後は一番当たりました
- 2B 級と 3B 級は、回答 0 問でも答えたあとでも EmbeddingGemma 2 と同じくらいでした。音楽は EmbeddingGemma 2 が一番でした
- 速さと VRAM では EmbeddingGemma 2 と SigLIP 2 が軽く、2B 級は 3〜4 倍、3B 級は 20 倍ほど遅くなりました

質問ごとの値と、モデルごとの設定の詳細は、開発用のリポジトリの記録にあります（公開していません）。

### エンコーダを書くときのヒント

- **問い合わせ側と文書側を分ける。** Shiken は、質問の説明と概念の語を `embed_texts` で問い合わせとして、データセットの項目（画像・音・文のファイル）を `embed_files` で文書として埋め込みます。モデルカードに問い合わせ用の指示文やプレフィックス（`query: ` / `passage: ` など）があれば、それに合わせてください。文の項目を `.txt` のファイルで渡す場合は、`embed_files` の中で文書として埋め込みます
- **返す前に長さ 1 に正規化する。** プーリング（最後のトークン、平均など）もモデルカードのとおりにします
- **`name` に設定を入れる。** 量子化や指示文、プロンプトの有無で空間が変わるので、たとえば `"ATH-MaaS/Ovis-Omni-Embedding-3B;8bit"` のように名前を分けます
- **画像の大きさの上限を決める。** Qwen 系の前処理は既定の上限が大きく、スマートフォンの写真をそのまま入れると VRAM があふれて極端に遅くなりました。100 万画素前後で切ると安定します。音声も、長い曲は最後の 2 分ほどにすると 8 GB の GPU に収まります
- **ファイルの埋め込みはディスクに保存する。** 大きいモデルでは埋め込みに時間がかかるので、付属の EmbeddingGemma 2 のエンコーダと同じように、パス・更新時刻・`name` をキーにして保存すると、2 回目から速くなります
- **8 GB の GPU で 3B 級を動かす。** bitsandbytes で言語モデルの部分だけを 8 ビットにし、画像・音声の部分は bfloat16 のままにすると動きました（`llm_int8_skip_modules=["visual", "audio_tower", "lm_head"]`）

## 埋め込みベクトルを小さくしたとき

EmbeddingGemma 2 の埋め込みベクトルは、先頭の次元だけを切り出しても使えるように作られています（Matryoshka 表現）。次元を減らしたり int8 にしたりしたときの結果は [試した範囲での結果](evaluation.md#埋め込みベクトルを小さくしたとき) にあります。768 次元のまま int8 にしても結果は変わらず、次元を減らしてもパーソナライズに要る回答の数は減りませんでした。
